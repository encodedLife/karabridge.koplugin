# The EPUB round trip

The end-to-end scenario that matters most: a real EPUB, a
real KOReader sidecar, and a live Karakeep server.

Last executed against a live Karakeep instance, API v1,
KOReader emulator `koreader-emulator-x86_64-linux-gnu-debug`.

## The fixture

`spec/fixtures/ebooks/karabridge-test.epub`, generated by
`spec/fixtures/ebooks/build_fixture.lua`.

Generated rather than committed as a binary: the content stays reviewable as
text, and every timestamp inside the archive is fixed so two builds are
byte-identical.

```bash
lua5.1 spec/fixtures/ebooks/build_fixture.lua
```

Each sentence earns its place.

| Sentence | What it exercises |
|---|---|
| `The first unique sentence in chapter one.` | plain ASCII |
| `Ein Satz mit Umlauten: ä ö ü ß.` | 35 bytes, 31 UTF-16 units — the offset unit question |
| `A sentence with an emoji 😀 in the middle.` | a surrogate pair: two UTF-16 units for one code point |
| `This exact sentence appears in both chapters.` | duplicate text; what text alone cannot resolve |

The repeated sentence is the important one. Highlighted in both chapters it
must produce two distinct Karakeep highlights that stay mapped to the right
local annotations — the case the old text-keyed deduplication collapsed into
one.

## Running it

The scenario is driven by a script rather than by hand, so it is repeatable.
It needs KOReader's `luajit` (for `socket.http`, `docsettings` and crengine)
and a Karakeep instance with an API key created for testing.

```bash
cd "$KARABRIDGE_KOREADER"/koreader-emulator-*/koreader
KO_HOME=/tmp/kb-rt ./luajit /path/to/roundtrip.lua
```

Everything it creates is titled `[KaraBridge Test]` and deleted afterwards.

## Result, step by step

### 1–2. A real EPUB, opened, with two highlights

The fixture is opened through `DocumentRegistry:openDocument` and rendered, then
two annotations are written to the sidecar as a reader would leave them: one
without a note, one with `Local KOReader note`.

```
geoeffnet, Titel: KaraBridge Test Book
Annotationen: 2
```

### 3–4. Upload

```
created=2 pushed=0 pulled=0 conflicts=0 unresolved=0 failed=0

Highlights auf dem Server: 2
  id=aaaaaaaaaaaaaaaaaaaaaaa1  note="(Chapter One)"
     offsets=0-41   text="The first unique sentence in chapter one."
  id=aaaaaaaaaaaaaaaaaaaaaaa2  note="Local KOReader note\n\n(Chapter One)"
     offsets=43-74  text="Ein Satz mit Umlauten: ä ö ü ß."
```

Exactly two highlights, the correct text, the note on the right one, and the
chapter folded in. **`unresolved=0`** — both positions were resolved rather
than falling back to `0,0`.

**The offsets are the proof the unit question was answered correctly.** The
umlaut sentence spans 43–74, a length of 31. The same string is 35 bytes. A
byte-counting implementation would have written 35, and Karakeep's reader would
have underlined four characters too many.

No API token appeared in the log.

### 5–7. A note edited in Karakeep, brought back

The note on the second highlight is changed to `Edited on Karakeep` through the
API, as the web UI would.

```
created=0 pushed=0 pulled=1 conflicts=0

Annotationen: 2
  [1] note=nil                  text="The first unique sentence in chapter one."
  [2] note="Edited on Karakeep" text="Ein Satz mit Umlauten: ä ö ü ß."
```

Read back from a fresh `DocSettings:open`, not a cached handle. Still exactly
two annotations — **no duplicate** — the note reached the right one, and the
first is untouched.

### 8. Idempotency

```
created=0 pushed=0 pulled=0 conflicts=0
Highlights auf dem Server: 2
```

Nothing created on either side, nothing changed.

### 13–15. A local edit after the remote edit

The note is changed in KOReader to `Edited again in KOReader` and synced.

```
created=0 pushed=1 pulled=0 conflicts=0
Highlights auf dem Server: 2  (keine neuen)
  dieselbe ID aktualisiert: aaaaaaaaaaaaaaaaaaaaaaa3
```

The **same** remote highlight was updated. No new one was created.

### 16–18. The duplicate-text case

The repeated sentence is highlighted in both chapters and synced.

```
created=2 pushed=0 pulled=0
Wiederholter Satz auf dem Server: 2   (getrennt gehalten)
Eintraege im Mapping: 4

-- and once more, with nothing changed:
created=0 pushed=0 pulled=0
Highlights gesamt: 4
```

Two distinct remote highlights for the same sentence, four mapping entries, and
a further sync changes nothing. This is what the position-based fingerprint is
for.

## What this run found

Two defects that the unit suite structurally could not.

**`fetchArticleText` undid the offset fix one layer up.** It still converted
HTML with `HtmlCleaner.toText` — which turns every tag into a space — before
`Offsets.locate` ever saw it, reinserting exactly the characters Karakeep's DOM
does not have. Fixed by returning the HTML untouched. A spec now asserts that a
separator is not inserted, and a second asserts the end-to-end offset for a
passage after a block boundary.

**`note` is required by Karakeep, not optional.** Found by the live integration
suite rather than this scenario, but the same class:
`zNewHighlightSchema` declares `note: z.string().nullable()` — nullable, *not*
optional — so omitting the key is a 400. Every highlight sent before then
happened to carry a note. See the CHANGELOG.

## What this does not prove

- **Anything about a real device.** This scenario ran in the emulator on
  x86-64, and proves nothing about hardware on its own. Storage
  paths, memory, touch behaviour and CPU speed all differ.
- **That the underline lands in the right place in Karakeep's web reader.** The
  offsets are computed the way the reader computes them and the lengths match,
  but nobody has looked at the rendered page. Note synchronisation does not
  depend on this — it uses the stored ID — so a misplaced underline would be
  cosmetic.
- **Behaviour with a large highlight set.** Four highlights is not two hundred.
- **PDF annotations.** The fixture is an EPUB. PDF positions are tables rather
  than XPointers, and `Identity.renderPosition` handles them, but no PDF has
  been round-tripped.
